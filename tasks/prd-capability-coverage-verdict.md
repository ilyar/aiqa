# PRD: достоверный вердикт при неизвестных возможностях моделей

**Статус:** проект требований; реализация не начата.  
**Дата:** 2026-09-05.  
**Основание:** анализ Dahl и текущего кода AIQA, HEAD `49e80db`.

## 1. Проблема

Пользователь запускает `compat,sdk`, ожидая оценку API и доступных моделей.
Если AIQA получает список моделей, но не определяет их возможности, модельные
проверки пропускаются. Итоговый `PASS` и 100% создают впечатление завершённой
проверки совместимости, хотя генерация не оценена.

В отчёте [dahl-compatible.md](/arch/project/aiqa-report/broker-report/dahl-compatible.md)
и [JSON](/arch/project/aiqa-report/broker-report/dahl-compatible.json)
от `2026-09-05T01:11:59Z`, созданном `1.0.0-alpha.4`, commit `e2bf833`:

- обнаружены и выбраны `MiniMaxAI/MiniMax-M2.7` и `deepseek-ai/DeepSeek-V4-Flash-0731`;
- обе модели имеют `NOT-EVALUATED`, их модули — `UNKNOWN / SKIPPED`;
- выполнены только два запроса списка моделей: native и OpenAI Go SDK;
- четыре проверки ошибок chat объявлены `not_applicable`;
- итог — `PASS`, core `2/2`, optional `1/1`, evidence `3/3`, `rankable: true`;
- target `summary.status: not-evaluated` расходится с `assessment.verdict: pass`.

Это доказательство недостаточного покрытия AIQA, а не несовместимости Dahl.
Исторический отчёт не является результатом повторного запуска текущего HEAD.

### Подтверждённый механизм в текущем коде

1. `internal/capability/classifier.go`: политика `inventory` сохраняет модель
   неизвестной при отсутствии capability evidence. Это намеренное поведение.
2. `internal/capability/router.go`: неизвестная классификация даёт пропуск модулей.
3. `internal/assessment/assessment.go`, `materializeModuleCoverage`: ветка
   `ApplicabilityUnknown` исключает требования из assessment через `continue`.
4. `internal/protocol/openai/runner.go`, `chatEndpointNotApplicable`: отсутствие
   выбранной исполняемой chat-модели превращается в неприменимость endpoint.
5. `summarize` оценивает оставшиеся требования и возвращает `pass`.

## 2. Цели

- Запретить общий `PASS`, если запрошенное модельное покрытие осталось неизвестным.
- Сохранить различие между неизвестностью, неприменимостью, пропуском и прямым FAIL.
- Сделать область проверки, её пробелы и следующий шаг видимыми в JSON и Markdown.
- Сохранить текущую политику запуска запросов и ограничения расходов.
- Применять общую семантику покрытия независимо для каждой protocol target.

## 3. Решения по области работ

Политика неизвестных моделей по умолчанию остаётся `inventory`. Этот PRD исправляет
оценку и объяснение результата; он не включает автоматическую генерацию для всех
неизвестных моделей. Существующие explicit `--model`, capability override и
protocol-specific fallback остаются способами уточнить или проверить маршрут.

Изменение уточняет [контракт маршрутизации](../docs/unified-model-routing.md):
inventory-only разрешает не отправлять запросы, но не разрешает считать
запрошенное модельное покрытие доказанным. Требования прежнего
[аудита](prd-unified-model-routing.md) об отсутствии запросов неизвестным моделям
и отсутствующим ID сохраняются; вывод о полноте покрытия пересматривается.

## 4. Пользовательские истории

### US-001: сохранить область проверки до исполнения

Как пользователь, я хочу видеть, какие модели и модули AIQA намеревался оценить,
даже если их возможности не удалось определить.

Критерии приёмки:

- [ ] План учитывает suites, выбранные модели, явные modules и default-enabled modules.
- [ ] Для каждой target/model/module сохраняются requested scope, applicability,
      execution и причина; отсутствие capability evidence не удаляет запись.
- [ ] Модули вне выбранной области не создают пробелов только потому, что они UNKNOWN.
- [ ] Автоматически выбранная модель без определённого маршрута сохраняет пробел
      в запрошенной модельной области; совпадающие ID разных targets не смешиваются.

### US-002: корректно агрегировать неопределённость

Как пользователь, я хочу отличать успешную проверку от отсутствия доказательств.

Критерии приёмки:

- [ ] Dahl-подобный запуск `compat,sdk` получает target/run `inconclusive`.
- [ ] Неизвестная модель без выполненных проверок остаётся `not-evaluated`;
      target получает явную причину недостаточного покрытия.
- [ ] Общий `rankable` равен false при неизвестной обязательной области покрытия.
- [ ] Успех SDK `models.list` не закрывает модельный пробел.
- [ ] Прямой core FAIL сохраняет приоритет над неизвестностью; пробел остаётся видимым.

### US-003: не подменять неизвестность неприменимостью endpoint

Как разработчик провайдера, я хочу, чтобы вывод о поддержке endpoint опирался на evidence.

Критерии приёмки:

- [ ] При неизвестных chat-возможностях provider chat checks имеют unknown applicability
      и skipped execution с причиной; они не становятся `not_applicable`.
- [ ] Отсутствие исполненного representative model само по себе не доказывает N/A.
- [ ] При подтверждённой неприменимости chat в выбранной области N/A сохраняется
      с основанием, без утверждения об отсутствии endpoint у всего провайдера.
- [ ] Route rejection и transient failure сохраняют root evidence и зависимости;
      неизвестность не порождает искусственные provider FAIL.

### US-004: объяснить результат и способ продолжить

Как пользователь отчёта, я хочу сразу увидеть, что было проверено и что осталось неизвестным.

Критерии приёмки:

- [ ] В верхней части Markdown видны область проверки и количество
      evaluated/not-evaluated моделей, а также unresolved coverage.
- [ ] Для Dahl явно указано: список моделей проверен, генерация обеих моделей не оценена.
- [ ] Guidance содержит сгруппированную причину и поддерживаемый способ продолжения:
      явно выбрать модель для существующего preflight либо задать capability по известному контракту.
- [ ] Guidance не предлагает исправлять провайдер без прямого доказательства дефекта.
- [ ] JSON и Markdown отражают один canonical verdict и одинаковые счётчики.

### US-005: закрепить контракт тестами и документацией

Как сопровождающий AIQA, я хочу исключить повторение ложного PASS на новых именах моделей.

Критерии приёмки:

- [ ] Добавлены локальные fixtures и сквозные проверки матрицы из раздела 8.
- [ ] Проверяются verdict, coverage, guidance, exit code и фактические HTTP-вызовы.
- [ ] Схема, документация и примеры синхронизированы с новым контрактом.
- [ ] Проходят `go test ./...`, `make check` и `make race` в подходящей среде.

## 5. Функциональные требования

- **FR-1.** Формировать область ожидаемого покрытия до исполнения; отсутствие
  evidence не должно уменьшать эту область задним числом.
- **FR-2.** `UNKNOWN` означает недостаток доказательств; `not_applicable` требует
  положительного основания неприменимости в выбранной области. Сохранять provenance.
- **FR-3.** Хранить пробелы покрытия отдельно от доказанных требований совместимости
  или как явно типизированные coverage records. Не объявлять неизвестный маршрут
  обязательной поддерживаемой возможностью провайдера и не создавать по нему FAIL.
- **FR-4.** Неизвестность в выбранной области с core-проверками даёт `inconclusive`
  при отсутствии прямого core FAIL. Только optional-пробел даёт `pass-with-gaps`.
- **FR-5.** При прямом core FAIL вердикт — `fail`; при оставшемся coverage gap
  `rankable: false` независимо от наличия FAIL. Без пробелов действуют текущие правила.
- **FR-6.** Пробелы одной модели нельзя закрыть PASS другой модели или другой target.
  Run агрегирует target verdicts по существующему приоритету, сохраняя blocking targets.
- **FR-7.** Conformance-проценты относятся только к известным требованиям и подписаны
  соответствующим образом. Coverage отдельно показывает expected, executed,
  unresolved и excluded counts с документированными единицами подсчёта.
  При unresolved > 0 нельзя показывать 100% как полное покрытие запуска.
- **FR-8.** Пропущенные проверки не считаются исполненными HTTP-запросами;
  coverage records не увеличивают transport counters или latency samples.
- **FR-9.** Устранить противоречие target `summary.status` и canonical assessment:
  синхронизировать status либо документированно удалить из сериализации устаревшее поле.
  Отдельный model `not-evaluated` допустим и не равнозначен target verdict.
- **FR-10.** `--fail-on core` и `any` возвращают ненулевой код при `inconclusive`;
  `never` возвращает 0, сохраняя честный verdict в отчёте.
- **FR-11.** Неизвестность сама по себе не включает новые сетевые probes.
  Explicit model preflight сохраняет переиспользование ответа без второго basic request.
  Генерация текста может расходовать токены; guidance не называет её бесплатной.
- **FR-12.** Сохранить billable-artifact, high-token и persistent-resource gates,
  exact inventory membership и target-local capability routing.
- **FR-13.** 429, 5xx, timeout, transport и runner errors остаются evidence/availability
  errors, а не доказанной несовместимостью. Зависимые проверки сохраняют `blocked_by`.
- **FR-14.** Существующая явно ограниченная область, например SDK-only `models.list`,
  может получить PASS только с явным указанием этой области. Не добавлять в неё
  непрошенные native-проверки. Нельзя автоматически переименовать `compat,sdk`
  в discovery-only после пропуска модельных проверок.
- **FR-15.** Явно запрошенный ID, отсутствующий в inventory, сохраняет прежний
  silent zero-match контракт: без синтетической модели, probe и нового coverage FAIL.
  Отчёт при этом не утверждает, что модель оценена, и показывает нулевое модельное покрытие.
- **FR-16.** Решение работает для произвольных новых ID; исправление не зависит
  от добавления Dahl, MiniMax или DeepSeek в name/provider rules.

## 6. Что не входит в задачу

- Изменение API Dahl, подтверждение реальной совместимости или производительности Dahl.
- Автоматический text fallback по умолчанию или расширение каталога возможностей моделей.
- Новые protocol endpoints, новые suites и нагрузочное тестирование.
- Перезапись исторических отчётов под видом нового запуска.
- Публикация, выпуск релиза или live-прогон как часть написания этого PRD.

## 7. Технические соображения

Точки изменения: `internal/capability`, protocol runners, `internal/assessment`,
`internal/result`, `internal/app`, `internal/report`, `internal/guidance`,
`schema/report-v3.schema.json`. Следует использовать один источник canonical
assessment для Markdown, JSON, ranking и exit policy.

Coverage не должен зависеть от наличия findings: guidance объясняет уже вычисленный
результат и не определяет вердикт. Не следует материализовать все неизвестные модули
профиля без учёта selected scope: это создаст ложные пробелы для image/audio и других
невыбранных возможностей.

Точные имена новых полей определяются при реализации. Перед изменением schema
проверить совместимость строгих consumers и fixtures; breaking change требует
версии схемы и migration note. Исторические отчёты остаются неизменными.

## 8. Матрица приёмки

| Сценарий | Ожидаемое поведение |
|---|---|
| Dahl inventory, `compat,sdk`, обе модели UNKNOWN | INCONCLUSIVE, rankable=false, две not-evaluated модели, guidance; только native/SDK models.list requests |
| Тот же inventory с произвольными незнакомыми ID | Тот же результат; нет зависимости от названий |
| Одна модель полностью PASS, другая UNKNOWN в core scope | Target/run INCONCLUSIVE; успех первой сохранён |
| Все выбранные core/optional проверки PASS, coverage полный | PASS без ложного предупреждения |
| Только optional scope остаётся UNKNOWN | PASS-WITH-GAPS; пробел явно показан |
| Core FAIL и UNKNOWN | FAIL плюс видимый пробел; rankable=false |
| Явный выбор неизвестной text-модели, preflight успешен | Существующий preflight и полная разрешённая suite; нет дублирования basic request; итог по evidence |
| Preflight получает 429/5xx/timeout | INCONCLUSIVE, один корневой error, dependent SKIP; нет provider incompatibility finding |
| Preflight получает явный model-route rejection | Прямой model FAIL; зависимые проверки не выполняются |
| Только подтверждённая image-модель | Chat N/A с основанием; image authorization gates сохранены |
| Неизвестен модуль вне selected scope | Не создаёт coverage gap выбранной области |
| SDK-only models.list | PASS ограниченной области; явно нет утверждения о генерации |
| Explicit ID отсутствует во всех inventories | Прежний zero-match контракт, нулевое модельное покрытие, нет model requests |
| Два targets: первый полный PASS, второй core UNKNOWN | Отдельные verdicts, run INCONCLUSIVE, второй в blocking targets |
| `--fail-on core / any / never` для Dahl fixture | Ненулевой / ненулевой / 0; verdict одинаковый |
| Повторный render одного результата | JSON и Markdown совпадают по verdict, scope, coverage; counters не зависят от render |

Локальная Dahl fixture должна быть самодостаточной: сохранить минимальные безопасные
inventory и ожидания в репозитории, без зависимости от абсолютного пути исходного отчёта.
Проверка схемы должна включать новые coverage states и target/model identity.

## 9. Порядок реализации и критерий завершения

1. Зафиксировать scope/coverage контракт и fixtures, воспроизводящие ложный PASS.
2. Добавить учёт неизвестности и исправить provider applicability.
3. Применить правила aggregation/ranking/exit и согласовать summary fields.
4. Обновить Markdown, JSON, guidance, schema, документацию и примеры.
5. Выполнить матрицу приёмки и repository gates; зафиксировать доказательства.

Успех измеряется отсутствием ложного PASS во всех fixtures с неизвестным core
покрытием, согласованностью всех представлений результата и отсутствием лишних
запросов. Полностью проверенные fixtures должны сохранять PASS.

Live Dahl запуск может отдельно подтвердить поведение на провайдере после реализации.
Локальные тесты доказывают исправление AIQA, но не совместимость Dahl и не выпуск релиза.

## 10. Открытые вопросы

Блокирующих продуктовых вопросов нет: область ограничена достоверностью оценки
при сохранении текущей политики запросов. Инженерное решение по форме coverage
records и необходимости смены версии схемы принимается до изменения сериализации,
с фиксацией в документации и тестами совместимости.
