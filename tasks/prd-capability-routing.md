# PRD: Capability-aware model routing

## Overview

AIQA currently applies Chat Completions checks to every model returned by `/models`. This produces false failures for image, embedding, audio, and unknown models. AIQA must classify endpoint-oriented capabilities, build an applicability plan, and execute only matching modules.

## Goals

- Preserve every discovered model in the inventory.
- Keep applicability separate from probe results.
- Prevent chat and chat-parameter requests from reaching models without evidence of chat capability.
- Represent inapplicable modules as `N/A` without changing probe status or score denominators.
- Support explicit capability overrides and conservative automatic classification.
- Add a billable, opt-in image-generation module with safe artifact validation.
- Route Official SDK suites by applicable module.

## User stories

### US-001: Classify model capabilities

As an API evaluator, I want evidence-backed capability classification so that AIQA does not infer chat support from the absence of image metadata.

Acceptance criteria:

- Explicit overrides have highest priority.
- Structured metadata and provider-specific rules precede conservative name rules.
- Conflicts resolve to `unknown` and preserve evidence.
- One model can have multiple capabilities.

### US-002: Route applicable modules

As an API evaluator, I want each model to receive only relevant requests so that unrelated endpoints do not create false failures.

Acceptance criteria:

- Chat and chat parameters run only for `chat.completions.text`.
- Models with positive non-chat evidence and models with conflicting evidence receive no Chat Completions requests.
- Provider-level chat error probes use a representative applicable chat model.
- Models without capability evidence default to low-confidence text chat; `--unknown-model=inventory` keeps them inventory-only.

### US-003: Report applicability

As a report reader, I want to see why a module ran or did not run so that `N/A`, policy skips, and compatibility failures are distinct.

Acceptance criteria:

- JSON includes capability evidence and module assessments.
- Markdown includes a routing matrix.
- Models with no executed module have `not-evaluated`, not `pass`.
- Inapplicable modules do not affect score.

### US-004: Test image generation safely

As an API evaluator, I want an opt-in image-generation module so that image models can be checked against their actual contract without uncontrolled cost or leaking artifacts.

Acceptance criteria:

- The module is disabled unless `--allow-billable-artifacts` is set.
- At most one artifact per model is generated by default.
- The response requires a non-empty `data` array and `b64_json` or safe HTTP(S) URL.
- Reports store only format, media type, dimensions, bytes, and SHA-256.
- Base64 payloads and signed URL queries never enter report observations.

## Functional requirements

1. Add endpoint-oriented capability and module assessment types.
2. Add conservative classification with CLI and JSON-file overrides.
3. Add `--module`, `--model-capability`, `--capability-file`, `--unknown-model`, `--allow-billable-artifacts`, and `--max-artifacts-per-model`.
4. Route native compatibility, model parameters, and Official SDK checks by module.
5. Run provider discovery once and select representative models per endpoint module.
6. Add the `images-generations` native module and safe artifact validator.
7. Extend the report schema and Markdown renderer additively.
8. Preserve the 2026-08 profile and add a modular 2026-09 profile.

## Non-goals

- Do not infer image generation from vision or multimodal input support.
- Do not implement semantic image-quality scoring.
- Do not execute billable media modules by default.
- Do not claim support for Responses, audio, video, or embeddings until their native probes exist.

## Technical considerations

- Keep the native implementation on the Go standard library.
- Treat `is_image` as a Vibecode-specific high-confidence signal, not an OpenAI standard field.
- Apply name rules only as positive, narrow evidence.
- Use `image.DecodeConfig` for PNG, JPEG, and GIF; parse WebP headers without adding a heavy dependency.
- Block loopback, private, link-local, and non-HTTP(S) artifact URLs.

## Success criteria

- A mixed catalog test proves that image-only, conflicting, and explicitly inventory-only models never receive chat requests.
- A disabled image module reports `SKIP`; its chat module reports `N/A`.
- Explicit overrides route custom models deterministically.
- All Go tests, profile validation, JSON schema validation, and documentation checks pass.
